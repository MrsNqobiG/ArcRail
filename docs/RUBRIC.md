## Money-path modules (closed list, for MC-07, MC-08 and the exit bars)
"Money-path module" means **exactly** the code implementing:
1. U1 amounts and the conversion module;
2. U4 credit decision logic (classification, dedupe, canonical source);
3. U6 inbound flow;
4. **U9 signer policy: every ADR-001 signer duty** (1 approval and assertion check, 2 shape allow-list, 3 limits and fee ceilings with the chain-ID pin, 4 consumed-approval replay record, 5 monitor-attestation protocol, 6 internal-move rule), **its signed-configuration load and its signing-log writer**, because each one is what stops or records outbound money (grown by fix block 12, LEDGER);
5. **U7 policy engine** (limits, thresholds, velocity, allow-lists, cross-border flag), because it decides DENY or ALLOW on money movements;
6. **U3 chain client** (quorum, disagreement detection, log paging), because wrong data there becomes wrong credits;
7. U10 outbound and case-return orchestrator, including the nonce writer;
8. U11 gas and dust accumulators and fee calculation;
9. U12 reconciliation and circuit breaker;
10. the ACL posting translator (CONTRACT §3 `postJournal`, the hold operations and `getResultByKey`).

Phase 2 records the matching source paths in `docs/MONEY_PATH.md`. The verifier recounts that file against this list, **mapping every named part of every item** (for example each ADR-001 duty in item 4) **to at least one listed path**, so a part implemented in a module that no listed path imports can't be left out, **and recomputes the import-graph closure**: every module that a listed path imports, directly or indirectly, is either in MONEY_PATH.md or explicitly excluded there with a reason (for example a pure logging adapter). Otherwise a helper kept outside the list would escape MC-01, MC-07 and MC-08. The list can only grow, and only by a LEDGER entry.

## Calibration probes (run 2026-10-02, before generation; patch budget 2 of 2 used)

### Probe G: a bad build that passes everything
**Scenario.** A build meets every check as first drafted, but tests reconciliation only on the happy paths S1–S5. On a T4 `REJECTED` after the chain has settled, the code logs and moves on. Nothing pauses, the item drops out of Rout, and a −A×k residual appears. Nobody notices, because "residual 0 in every test scenario" was met by choosing happy-path scenarios only.

**Patch 1:** the reconciliation assertion is required for every failure path and every flow cell, with counts matched. That is now MC-05, which counts **cells**, not rows (strengthened by fix block 1).

### Probe F: a good build that fails the rubric
**Scenario.** Exhaustive `switch` statements with an `assertNever` default that the compiler proves unreachable. "100% branch coverage" can't be met without deleting the guards.

**Patch 2:** MC-07 means 100% of **reachable** branches. A branch may be excluded only if all of these hold:
- it is a compiler-proven exhaustiveness guard;
- it is listed in **`docs/COVERAGE_EXCLUSIONS.md`** (created in Phase 2) with file:line and reason;
- the verifier recounts it.

This **changes how a KICKOFF §3 exit bar is measured.** Whether that is a relaxation is for the human to judge, so **it needs explicit human acknowledgement at G1.**
