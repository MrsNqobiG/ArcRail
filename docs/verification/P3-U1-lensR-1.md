**D1 detail.** The type-aware lint lets `p % 1` through, because `p` is on the allow-list. Semgrep can't see types, so it flags any `%` with a plain number literal. ci.sh:103 uses `x * 100 - (x * 100) % 1` as one of its own self-test plants for exactly this rule. The unit therefore fails a mandatory lint, and `bash scripts/ci.sh` would fail at the Semgrep MC-01 stage. A fix needs an integrality check that uses no arithmetic operator with a number literal. Note that `Number.isInteger` is itself flagged by `mc01-number-parse`. This is the author's choice: for example, an exact membership check against the integers 0 to 18, or relying on `BigInt(p)` throwing a RangeError on a non-integer, NaN or ±Infinity. Re-run both layers afterwards.

**D2 detail.** In /tmp plants (each a real copy of src/ plus one planted module), the rule returned **no finding** for each of these re-brands:
- object destructuring: `const { v } = { v: a + b }; nativeWei(v)`
- array destructuring: `const [s] = [a + b]; nativeWei(s)`
- a generic type-parameter assertion: `function id<T>(v: unknown): T { return v as T; } const x: NativeWei = id<NativeWei>(a + b);`. The REBRAND-CAST check at :221 looks only at the literal target type `T`.
- `any`: `const s: any = a + b; const x: NativeWei = s;` and an `any`-returning helper. MC01-any covers money-path files only, but this rule covers all of src.

The header's "inspection-only limits" (:26-29) mention none of these. It also says taint does not flow through object properties, but my plant `const o = { v: a + b }; nativeWei(o.v)` **was** flagged, so the stated limits are inaccurate. The rating is minor: each case is a deliberate evasion, the compiler still blocks every implicit mix, and no money moves.

**D3 detail.** Lines 20-22 of the header say "a CBS minor amount above the signed 64-bit maximum is refused with `CbsMinorOverflowError`". That isn't true of the constructor or of the sanctioned arithmetic. I reconstructed both in a /tmp copy:
- `addCbsMinor(cbsMinor(CBS_MINOR_MAX), cbsMinor(1n))` returns 9223372036854775808 and throws nothing;
- `cbsMinor(2n ** 64n)` is accepted, and amounts.test.ts:14 even asserts acceptance of a 31-digit CbsMinor.

CONTRACT §6 says that amounts are arbitrary-precision inside the adapter and that "the call is rejected" when m > CBS_MAX. So the guard on a summed CBS amount, for example the T4 leg `A + fee` built with `addCbsMinor`, belongs at the CBS call, which is the ACL translator. But U1 keeps `checkCbsMax` private, and no test or MONEY_PATH anchor assigns that guard to the translator. Fix: correct the header claim, and either export the guard or apply it in `addCbsMinor`. Then route a "guard every CbsMinor at the CBS call" requirement to the translator unit.

**D4 detail.** The CONTRACT §6 heading says "U1 is the only implementation" of the whole table, and the table includes the "any → display" row (integer formatting only, never 18 dp). U1 implements no display formatter. KICKOFF assigns display to U11. Without a LEDGER or CONTRACT routing note, U11's display code would become a second conversion module. Fix: add an integer-only display formatter to U1, or record the routing.

**D5 detail.** The KICKOFF U1 row lists the registry fields as "address, decimals, status". `AssetView` has address and decimals, plus `creditView`, but no status field (for example enabled/disabled, or the verification state of the constant). The relayed unit spec doesn't mention status, so this is minor and inspection-only. Fix: add the field, or record in LEDGER that `creditView` and the C-id list stand in for it.

**Observation (not a defect).** `CBS_MINOR_MAX` is fixed at 2⁶³ − 1, while CONTRACT §6 defines CBS_MAX as "the CBS integer max, Q-C4", which is still open. The header says this bound "only ever refuses". That holds only if the real CBS maximum is at least 2⁶³ − 1. If Q-C4 returns a smaller width, the bound must become the CBS's own value, with the precision cross-check from CONTRACT §1.1. Track this under Q-C4.
