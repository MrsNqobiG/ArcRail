**D1: interface and abstract-class dispatch evades REBRAND-ARITH and REBRAND-CROSS.** Taint is attached to the implementing method's symbol (`Impl.get`). A call made through the interface or base type resolves to a different symbol (`Src.get`), so it is never tainted. These four plants in a /tmp copy were all reported clean:
```ts
// src/zz-impl.ts
export interface FeeSource { fee(): bigint }
class Rpc implements FeeSource { fee(): bigint { const gasUsed = 21000n; const price = 20_000_000_000n; return gasUsed * price; } }
export const feeSource: FeeSource = new Rpc();
// src/zz-plant.ts
export const x = nativeWei(feeSource.fee());            // MISSED (REBRAND-ARITH, cross-file)
```
The same pattern also escapes in these forms: a class property through an interface (`readonly v: bigint = a * b`), an `abstract class` base, an array of interface type, and a cross-unit relabel (`get(): bigint { return wa; }`, then `usdcUnits(s.get())`). The control plant `cbsMinor(21000n * 2n)` is flagged. This matters because the rail is built on ports such as `ChainReader` and the CBS port, so an implementation that does arithmetic and a caller that brands the result through the port type is a realistic shape (for example a gas-fee helper). Why minor and not blocking: the mandatory MC-01 lints are clean; no current src code takes this route (the real-tree run is `[]`); and the defect is a false negative in a defence-in-depth rule, not a money path that loses value today. Suggested fix: when a method, property or getter of a class is tainted, also taint every interface or base-class member it implements or overrides (`checker.getPropertyOfType` on each heritage type), or flag any constructor call whose argument is a call through an interface-typed receiver. Then pin the case with a plant test, or else list it as a documented limit L6 with a pinned test.

**D2: two unbound copies of the USDC constants.** U1's registry hard-codes chainId '5042002', decimals 18n and 6n, and the address `0x3600…0000`. U2 already holds the same C-01/C-10/C-11/C-12 values and states that code must load Arc values from U2 "and nowhere else". U1 can't simply import U2 at runtime, because U2 imports `nativeWei` from U1 (src/chain/config/index.ts:15), which would create an import cycle. But no test binds the two copies. A future change to constants.md applied to one copy only (for example the ERC-20 address, or a decimals correction) would let the conversion module and the chain client disagree, with every test still green. All values are correct today (K14), so this is minor. Suggested fix: add a test asserting `USDC_NATIVE.decimals === BigInt(ARC_TESTNET.nativeDecimals)`, `USDC_ERC20.decimals === BigInt(ARC_TESTNET.usdcErc20Decimals)`, `USDC_ERC20.address === ARC_TESTNET.usdcErc20Address` and `USDC_*.chainId === String(ARC_TESTNET.chainId)`, or add an equivalent check against the docs/constants.md rows. Also record the deliberate duplication in a LEDGER line.

Dismissed observations: (a) `cbsPrecision(-0)` is accepted. `BigInt(-0)` is `0n` and `String(-0)` is "0", so it behaves exactly like p = 0, and nothing can be misposted. (b) `UnitTag`'s `${number}` hole admits "CBS_MINOR:X:2.5" at the type level. This is a wire-format string that U1 never parses, every p reaching a conversion goes through `cbsPrecision`, and the MC-01 lint exempts it by design. (c) A ternary that selects one of two raw operands is not flagged by the re-brand lint. It is not arithmetic, so this is correct.
